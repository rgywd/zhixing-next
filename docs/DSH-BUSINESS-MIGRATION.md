# DSH 业务迁移与 Python 服务退役

2026-10-29。本文区分源码、独立宿主验收与生产切换；正式发布和切换不能从源码完成推断。

## 当前分工

| 内容 | 负责方 |
| --- | --- |
| 模型、线程、执行、队列、取消、工具、插件 | DSH 原生宿主 |
| 搜索、记忆、定时任务 | DSH 已有能力及实际安装配置的插件 |
| 财务、健康、同餐付款业务 | 知行插件，在 DSH `zhixing_business` 原生存储域内提交 |
| 文件归属、持久化、工作区、处理与交付 | DSH 线程、附件与 `present` |
| 消息输入、文件传输、预览、分享 | App 和薄 HTTP 出口 |
| 本机草稿与阅读缓存、密码库、设备权限 | App；不成为服务端资料库或记忆系统 |

财务健康保留金额精度、预算继承、季度付款和月成本、未知日期范围、修订冲突与重试去重。实际饮食及明确付款一次提交，纠正修改原记录。早期资产观察保留为只读历史，不能当作当前余额。用户没给出的金额、摄入或健康事实不会由服务层补造。

`zhixing_service` 自动从 DSH 已消费的用户消息和当前线程带入来源编号。排队消息尚未进入原生消息投影，不会被误认成本次写入来源。模型和用户不用寻找会话 ID。

App 移除自建记忆、资料库、搜索供应商、旧人格和模型供应商管理入口，停止轮询 `/resources`。宿主模型选择仍可直接使用；“模型与插件”说明如何使用 DSH 能力。照片文件仍能进入聊天，“本对话文件”从原生线程归集，不新增索引或发布副本。

## 数据迁移

迁移脚本只在运维时运行，不需要保留 Python 服务。

1. 在新目录执行 `python3 scripts/export-dsh-business.py --database /var/lib/zhixing-next/app.sqlite --output /私有备份/business.json`。SQLite backup API 包含 WAL，生成完整 `.sqlite` 备份和 15 张业务表的 JSON；不覆盖已有备份。
2. 将 `ZHIXING_DSH_BUSINESS_IMPORT` 指向经核对的 JSON，启动独立 DSH 宿主。只允许空业务域导入；核对表集合、行数、来源引用和内容指纹，原生提交后读回再验。重复启动识别相同指纹，不覆盖之后在 DSH 的写入。
3. 比较原始业务表的完整哈希，再逐项比较账本、预算、健康档案、体重、规则和汇总。原始数额、未知字段、请求回执、修订与来源一起迁移，不只迁总额。
4. 使用同一个冻结快照运行 `python3 scripts/archive-dsh-legacy.py --database /私有备份/business.sqlite --data-root /var/lib/zhixing-next --output /DSH工作目录/迁移前资料`。旧对话、记忆、偏好和任务保存为普通文件；附件逐个检查原始大小及 SHA-256。缺失或已变化的原件直接报错。
5. 完整 SQLite 备份包含运行配置，保存在管理备份目录，不能放入 DSH 工作区。可读归档只导出明确的用户资料表，不导出供应商凭据表。原始数据目录和旧发布保留供核对、回滚；不删除用户资料。

旧对话以历史文档保留，不伪造成 DSH 原生线程。旧记忆整理、心跳和任务不会自动恢复；当前核对到的“每周财务回顾”为暂停状态，保留该状态。是否安装记忆插件、把哪项历史指令设为 DSH 调度，由实际需求决定。

## 部署与切换

`deploy/install_dsh_runtime.sh` 安装固定的 Linux x64 Node 24.21.0、DSH 0.2.2-alpha.2 和 pnpm 11.28.5，校验官方 Node SHA-256；不替换机器的系统 Node，也不启动服务。其他架构需使用对应的官方构建并重新验证。

独立运行目录为 `/opt/zhixing-next/runtimes/dsh-0.2.2-alpha.2`；服务模板为 `deploy/systemd/zhixing-dsh.service`。以 `zhixing-next` 用户运行，工作目录 `/var/lib/zhixing-next/dsh-workspace`，DSH_HOME `/var/lib/zhixing-next/dsh`，私有环境文件 `/etc/zhixing-next/dsh.env`。默认模型及额外供应商配置保存在该 DSH_HOME 的 `host.patch.yml`；CLI 的 `--patch` 必须位于 `--no-open`、`--port` 等内层参数之前。沿用宿主预设和权限，不在本插件添加工具白名单或执行预算。

先在另一个本机端口预部署，配置实际模型、原生搜索凭据及本插件，验证真实对话和数据读写。移动 API 继续使用原 HTTPS 入口及服务令牌；原生 DSH Web 先绑定 localhost。只有配置并核验宿主自己的认证后，才向外开放其管理页面。

0.2.10 还会轮询旧资源接口，新后端不提供这些接口。因此必须先准备配套新客户端并完成真实模拟器验收，不能只替换后端就声称迁移完成。创建正式标签和 Release 仍需用户明确要求。

正式切换时：确认没有正在写入的旧任务，停用 `zhixing-next-api` 和 `zhixing-next-worker`，立即做新的冻结备份、导出和归档，再在空原生域导入最终版本；核对通过后让 DSH 占用原 API 端口。`systemctl disable` 防止旧 API/worker 重启；不处理其他应用的 Python 服务。验证真实手机请求、模型调用、原生写入、重启持久化、上传预览分享，再记录切换回执。

失败时先停止新宿主再恢复旧端口，不能让两个服务同时接收写入。切换后已有新写入时，不能直接回退到过期 SQLite；先保留原生域并核对期间的新增记录，再决定恢复方案。
