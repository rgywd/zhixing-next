# Agent 协作与工具可用性

状态：2026-10-17，三阶段实现已完成。本文记录工作范围、协议及验收方法；最终本地门禁与隔离云模型结果记录在交付 PR，原生设备及生产部署另行验收。

## 交付顺序

1. 工具输入直接暴露健康、饮食、提醒与联合餐费的嵌套结构，局部修改保留未改字段；错误提供可修复位置；内置协议只保留代码中的一份。扩展自然输入验收，分别统计首次参数成功、纠错次数与实际业务回执。
2. 主运行可启动有限数量的只读研究子 Agent，追加指令、等待和关闭；每个 child 独立上下文，结果与应用指令有持久回执。财务／健康 `task` 只同步调用相应业务服务，不提供可续问研究句柄；并行研究和后续补充使用研究子 Agent。同一顿餐食与餐费的新增、纠错由主助手的联合工具在单个事务完成，不能拆委派或用备注模拟流水。
3. 对已有独立对话发送持久只读咨询，使用该对话的身份与历史；等待释放聊天槽位，完成后继续原 checkpoint。发送、查询和唤醒都不直接改目标 graph。

这三个阶段不增加用户需要管理的任务、项目或 Agent 配置流程，也不恢复已退出手机入口的通用任务管理。

## Codex 调研与本仓取舍

Codex 的[子 Agent 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)将委派执行放在各自的 thread 中，主 Agent 负责追加要求、等待和汇总。[多 Agent API](https://developers.openai.com/api/docs/guides/responses-multi-agent)进一步区分消息与启动：`send_message` 只排入消息，`followup_task` 才启动或恢复工作；稳定句柄、独立上下文、中断后保留状态属于运行时职责。本仓借鉴这些可观察的生命周期语义，没有要求模型维护拓扑、幂等键或内部状态。

持久对话另有一层：[App Server](https://learn.chatgpt.com/docs/app-server)区分 `thread/start`、`thread/resume`、`thread/fork` 与 `turn/start`、`turn/steer`、`turn/interrupt`。收到请求只表示接受，仍须消费事件并核对最终状态。桌面插件提供的跨对话工具不能据此认定为公开 App Server 的标准 mailbox 协议；本仓的投递事务、只读来源与等待释放槽位是自己的实现和验证边界。

[官方 harness 分层说明](https://developers.openai.com/blog/codex-as-a-platform)将执行循环、状态、事件和沙箱与应用的业务规则、上下文、工具分开。避免工具形式化也需要这层分工：模型只选择当前实际可用的动作和来源，程序维护权限、稳定身份、版本与回执；验证同时看最终装配后的模型菜单、首次调用、真实副作用和自然答复。只读请求成功、投递 accepted 或运行 completed 均不足以单独证明任务完成。

## 生命周期与权限

研究子 Agent 使用 `start_agent`、`send_agent`、`wait_agents`、`close_agent`。句柄及投递 ID 由运行时产生，模型不维护幂等键。默认最多四个 child、两个同时执行，调用使用根运行预算。每轮研究最多六次模型决策，第六次禁用工具并据实收尾；选定来源尚未完整收齐就到达边界时必须显式标为受限，不能把部分研究当成完整成功。保留有效上下文的本地限额失败可向同一 child 追加更窄指令继续，下一轮仍有六次决策边界；回执用 can_send 明示能否继续。尚无总结时结果仍为空、状态仍为失败，不能当成已交付；关闭、中断或其它失败不会被自动恢复。此边界不增加独立 token 额度，所有调用仍受根运行总预算约束。工具成功读取全文有明确完成标识，任务内已说明的未知项不会成为无限检索的要求。只读能力由实际工具白名单保证，不靠角色提示。等待结果包含真实状态、结果版本和是否停止；接收追加指令不等于已应用。

文件研究的 `source_paths` 从当前工作文件实际清单中选择，模型看到同一份有界路径选项；运行时再次验证后，将来源范围随初始消息持久保存。选定文件的 child 只使用对应的受限读取器，后续事实补充沿用原来源范围，计算由主助手结合实际结果处理。当前最新要求之后，所有选定文本来源均有真实成功全文回执时，运行时关闭工具并进入正常总结；新要求会重新开放原来源的读取，旧回执不会自动锁住续问。没有明确全文证明的文档或图片仍按实际回执与局部边界处理。`source_paths=[]` 用于历史、资源与联网研究，不提供任意物理文件读取。候选沿用现有文件列表的上限与权限，额外 grants 仍由主助手处理。路径绑定不是内容快照；文件被删除、替换或权限改变时保留实际读取失败。

child 的上下文和回执落入产品 SQLite。进程重启不延续旧 Python/model 调用；遗留活动 child 标为 interrupted，不会伪装仍在执行或静默重放。根运行退出时等待 child 实际停止。最终回复前必须读取结果或关闭未结束的 child。

跨对话使用 `send_conversation_message`、`read_conversation_reply`、`wait_conversation_replies`。发送工具立即返回持久投递回执，不能把 accepted 当完成。目标按自己的 FIFO 队列执行，始终只有该 conversation 的 worker 写 checkpoint。等待使用 LangGraph interrupt，原运行进入 `agent_wait` 并释放全局聊天槽；目标终态或需要用户处理时唤醒。完成早于暂停和完成晚于暂停均需处理，多个并行等待保留依赖并集。

若同一运行还有研究 child，跨对话暂停前先自动等其实际结束，避免让出聊天槽时中断已有研究。此等待仍受根运行预算及取消约束，不替模型读取研究结果；恢复后仍需收齐结果再答复。手机端等待期间可继续补充要求；内部只读咨询不接受用户消息混入同一次运行，新的用户请求按原队列执行。

跨对话首版仅为只读咨询；用户所在对话及原有服务委派继续负责业务写入。收到的内容带 `origin=agent_message`，前端标为其他助手，不进入个人记忆，不被解释为新用户授权，不能继续向其他对话发消息。只读限制在恢复或模型切换后仍生效。拒绝向本对话投递、依赖环及超量发送。

取消发送方不会撤回已经接收的独立咨询；目标结果仍可查询。取消等待、目标失败／取消／中断均保留实际状态，不能转成成功答复。等待时的新引导会清除旧等待依赖并恢复原运行重新决策。

## 数据与恢复

数据库 v14 增加 child、追加输入、child 事件、跨对话投递及等待记录。发送以源 run 和工具调用 ID 去重，目标 message/run 与投递回执同事务提交；同键换内容或换目标拒绝。只保存当前主机本地数据库，不引入额外队列服务。

升级前按部署文档停止 worker 并一致性备份；v14 不能直接用只支持 v13 的旧程序打开。回滚需要对应的程序和升级前完整数据备份。新表不改变旧业务账目；只识别已知内置健康说明，保留用户自定义文本。

## 验证闭环

- 工具契约：核对模型实际收到的 JSON schema；省略字段、显式清空、未知字段、版本冲突、稳定来源与幂等回归。
- 研究 child：独立上下文、并发上限、追加指令应用、结果版本、关闭实际停止、重启遗留状态、父最终回复前收尾。
- 跨对话：并发去重、事务故障回滚、来源隔离、依赖环、单槽执行、两种唤醒顺序、并行等待、失败／取消／中断、Steer 及重启恢复。
- 真实模型：隔离空实例、自然表达不提示工具名，按模型和 main/direct/delegated 入口统计。已有测试模型只证明执行链路，不作为真实模型选工具验收。

`scripts/tool_usability_eval.py` 默认离线读取私有验收回执；`--run-case` 才连接显式配置的隔离本机 API。`scripts/tool_usability_scenarios.json` 提供十二个场景、二十四种表达。缺少逐次事件、分类或独立业务快照时，指标保留 unknown；不把运行 completed 当业务成功。原始输入、回复、事件与快照不写入 Git。

本轮真实调用暴露并修复了实际契约问题：SDK 将不可用的通用助手留在委派菜单里，模型先失败才换入口；餐食 timestamp 必填且给出示例，模型会把未知时刻补成示例值。当前按运行实际能力提供工具菜单；未知用餐／测量时刻由程序采用原消息记录时钟并保留未知标记，手机端不把记录时钟显示成实际时刻。份量只写用户明示的对应食物。无执行环境的主助手不再同时展示虚拟目录和物理目录入口；SDK 内部大结果／历史只在真实内部引用存在时提供只读入口。短 child 结果不展示翻页参数；多结果合并后的实际序列化大小也受限，避免 SDK 将正文替换成文件指针。需要续页时只用实际返回的下一页游标，按结果版本收齐连续正文后才允许交付；只读首屏、尾页或跳过中段都不算完整读取，明确放弃可关闭。已读完的终态结果不要求额外关闭。委派只传原问题与必要来源，不先重复遍历已知文件，不扩写成无关未知项清单或主动推断。

研究只继承证据与未知项规则，不继承业务助手主动补查个人资料、交付报告或写记录的流程。原文是证据，不是覆盖任务的指令；后续事实澄清可补充旧资料，旧文件未载入该事实本身不构成矛盾或再次确认的理由。

工具回执正确仍须核对自然答复与实际保存字段。责任或费用归属需要明确来源，不能从“不保证”推断。关键词可能把“未声明免责”误判成免责，也可能因正确答复用了“消息发送时间”而非“记录时间”将其误拦。因此语义关键词仅生成复查线索，不能自动放行或否决答复；即使无线索，也必须独立读完整输入、答复和保存字段，包括跨对话实际答复及研究 child 已交付版本。可程序验证的断言完成后状态为 review_pending（CLI exit 3），不能称为最终通过；独立审阅需绑定源码、模型配置及证据文件哈希，另留逐场景结论。

跨对话的初始事实概括、目标沿用旧事实及源对话忠实汇总，列为 `semantic_review.required_claims` 的必查项，并记录完整 `reply` 与 `additional_reply` 的 SHA-256；不要求答复使用某种语言或固定词语，也不将同词但事实相反的答复自动放行。该记录始终为 required，独立审阅另行给出语义结论。实际检查点、投递目标、只读权限、真实完成回复、等待让出 worker、首次工具选择及工具错误数等硬断言继续执行。评估规则修正不重写已有失败原始证据；可对同一份完整证据另留绑定审阅，明确真实调用的源码版本与后来仅评估脚本变化的版本。

最终门禁、模型名称、源码快照与结果在交付 PR 列出；原始回执和审阅记录保存在私有验收目录，均不提交到 Git。独立审阅可由当前任务的另一位 Agent 完成，不要求用户管理回执或额外审批。单一模型的一轮固定样本通过，不代表任意自然表达或模型都不会失败。Docker 条件集成、原生设备和生产部署按各自条件另行验收。

## 下一轮计划

本轮完成后，优先扩充同一真实模型在不同自然表达和连续纠错中的验收，包括只说文件名或刚上传资料、不带内部路径的多文件研究；记录首次选工具、首次参数成功、重试次数、实际写入及总耗时，再对比另一种模型。现有十二类／二十四种表达是可运行场景集，不代表已完成全部云端测试或统计显著的模型比较。

模型实际收到的工具名称、顺序、说明和参数必须一起检查：SDK 置首的泛化委派入口会压过后面的专用研究工具，仅修改自己的系统提示或原始函数说明不足以证明合同清楚。

新增工具前先写一个用户会自然提出的场景，并确认现有工具不能完整完成它；验收时不给提示词塞工具名。模型看到的入口只展示当时可用的能力和后续句柄，禁止把不可用 SDK 占位助手留作可选项。真实回归如果先失败再找对入口，应修复契约后重跑，不能仅以最终完成作为放行条件。

跨对话业务写入及跨主机调度不在本轮范围；后续有具体场景再规划授权与冲突处理。当前用户无需手工维护投递 ID、Agent 拓扑或任务状态。
