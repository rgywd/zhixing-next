# 知行财务与饮食体重管理产品文档

状态：2026-10-15，0.2.0／0.2.1 已发布；后续首页与 AI-first 记账调整以当前源码为准。本文的完成条件仍是验收要求，不表示每项已通过。源码与验证边界见[实施方案](FINANCE-HEALTH-IMPLEMENTATION-PLAN.md)，正式交付回执见[发布说明](RELEASE-0.2.0.md)，项目取样见[GitHub 调研](AI-FINANCE-HEALTH-RESEARCH-2026-10-14.md)。

知行帮助用户在日常聊天中记录消费与饮食，围绕可调整的结余目标和饮食约定提供建议、跟进与回顾。本版以本人手机可以脱离开发电脑持续使用为交付终点。

## 用户需求与产品范围

| 已确认的需求 | 本版行为 |
| --- | --- |
| 降低日常开销并保留期望结余 | 记录消费，分别呈现日常趋势、全部支出和结余预测，解释偏离原因 |
| 饮食管理是体重管理的重点 | 聊天形成饮食约定，记录实际饮食，提供下一餐建议并跟进 |
| 身体条件会限制活动 | 活动限制进入推荐约束，步数作为记录，不自动增加运动目标 |
| 数字与规则会随生活变化 | 收入、预算、目标、饮食约定、偏好与提醒均可通过对话或直接操作修改 |
| 主 Agent 与多个子 Agent 继续存在 | 主知行统筹，财务与健康服务可直接使用，也可由主知行委派 |
| 任务和工作目前不需要 | 移除独立工作页、项目管理、任务模式和通用计划管理入口 |
| 做完两个服务后正式发布 | 同版后端、独立 Android 安装包、实体手机验收与发布附件共同完成 |

首版覆盖文字、图片、直接操作三种输入。银行直连、自动读取全部支付记录、健康平台自动同步、完整食物数据库、训练计划和通用自动化平台放在实际使用反馈之后。

用户的财务金额、身体测量值与健康限制属于运行时个人资料，不作为仓库常量、公共样例或测试夹具。本文中的场景对话均为虚构示例。

## 日常使用场景

### 说完就能记录

用户说“午饭二十多，具体二十四元，鸡腿饭，米饭剩了一半”。知行保存一笔明确金额的餐费，以及一顿包含食物和剩余份量描述的饮食记录，返回简短回执。只说金额时只记录支出；只发菜品照片时不推断支付金额。

用户继续说“刚才记错了，是昨天的午饭”，两份关联记录一起纠正。同餐费与实际饮食通过同一 SQLite 事务保存；任一项失败均回滚，重试原请求不会重复新增。

截图、文字和服务页面操作进入同一份服务数据。用户不必先选择子助手，也不必逐条审核清晰记录。只有金额、对象、日期或实际行动的歧义会改变结果时才简短追问。

日常入口采用 AI-first：“记一笔收支”、首页记账快捷入口和记录空态均直接进入财务 AI，优先继续已有对话，不先展示表单，也不代发模板消息。用户已有输入与附件保留。手动补记位于记录卡底部，仅在用户主动需要时使用；既有未完成编辑、预算调整、逐条纠正、关联退款和删除仍可继续。

### 先聊规范再决定吃什么

用户说明口味、饮食限制、用餐便利程度和预算，也可以直接提供已有饮食规范。清楚表达的要求直接保存，并用一句话反馈理解；AI 提出的新规范保留为建议，用户采纳后才生效。

用户问“今晚吃什么”，知行结合当前约定、最近已记录饮食、用户提供的可选餐食和可用餐费，给出少量可执行选择，说明份量与替换方式。用户说“今天只能点外卖”时，建议立即按现实条件调整。

### 按约定跟进

用户约定用餐时段提醒与晚间回顾。到约定时段，手机提醒用户查看饮食建议或顺手记录；用户打开后看到结合最新记录的建议。记录偏离约定时，知行解释影响，并给下一餐的一项调整，不用断食、额外运动或责备作为补偿。

用户说“今天别催”“以后晚饭再提醒”“这条规范先暂停”，对应范围立即更新。遗漏记录只表示未知，不代表没有进食或没有消费。

## 手机入口

当前底栏为“首页、生活、知行、施工中、设置”。财务和健康位于生活子页；施工中只显示功能待定。旧工作、项目管理、任务模式和通用计划入口已移除，历史对话与运行回执保留。

| 页面 | 首屏内容与主要操作 |
| --- | --- |
| 首页 | 本月预算简报、下一餐或今日跟进、简短体重趋势、常用与最近对话 |
| 财务 | 剩余可花与结余预测、日常与全部支出；记账优先进财务 AI，手动补记为辅助入口 |
| 知行 | 主助手对话，自动调用对应服务；无需选择任务模式 |
| 健康 | 下一餐建议、当日饮食与约定、体重趋势、健康对话 |
| 设置 | 模型、人格、助手、资源、连接，以及服务目标和提醒偏好 |

首屏优先显示有依据的结果，空状态给出一个起步动作。财务与健康页面复用共享对话、附件和纠正能力；键盘展开时收起速览。所有主页面、子页面、320 dp 窄屏、日夜主题和 Android 返回行为遵循[共享 UI](UI.md)。

## 财务服务

### 目标与预算

目标结余、预计到手收入、固定支出、计划大件和日常预算独立保存。用户可以先给其中一部分，不要求填完档案才记账。缺少收入依据时可以使用支出上限；缺少两者时先记录与回顾，不展示没有依据的“能达标”。

目标结余约束整体资金安排，日常预算表达用户希望压低普通消费的意愿。两者同时存在，不能把可满足结余的最大支出直接当作建议花完的额度。

预算默认沿用最近有效设置，允许指定某个月或从某日生效。自然语言修改后，页面与两个 Agent 立即使用相同的当前值。修改未来计划保留历史实际收支；需要重算历史分类时按用户要求处理。

### 支出与统计口径

支出至少区分日常、固定、一次性，并支持餐饮、购物等少量可修改类别。发生日期和录入时间分别保存，补记归入真实发生期。

大件可从日常趋势中排除，但进入全部支出与结余。固定费用的预算预留与真实支付关联抵扣。内部转账与信用卡还款不重复算消费，退款关联原消费并冲减对应支出；账户余额观察值不推导为收入。

| 用户问题 | 展示结果 |
| --- | --- |
| 这个月花了多少 | 选定周期内全部已记支出，说明包含哪些费用 |
| 普通日常有没有变贵 | 同口径的日常支出趋势，不混入大件或把漏记天当零消费 |
| 接下来还能花多少 | 基于有效预算、已花支出和剩余承诺计算的可用额度 |
| 月底能留下多少 | 已知收入与支出、待发生安排及日常预测共同构成的估计 |
| 哪里值得调整 | 按实际类别变化解释原因，给少量可操作建议 |

不同算法、不同覆盖期的日均可以并存，名称与范围随结果显示。用户自己给的估计保存为估计基线，不生成虚构流水。

### 轻松开始与纠正

可以从当前开始，也可以提供账单截图、文件或本月累计。累计汇总与后来补入的明细需在后台衔接，避免叠加计算；不把找原话和逐项对账变成使用门槛。

同一请求重试不能重复入账。不同来源疑似同笔消费时，优先用来源和内容核对；证据不足时不因同额同日就删除真实消费。清晰记录直接保存，只有确会影响总额的重复歧义才追问。

## 饮食与体重服务

### 当前资料与饮食约定

服务保存用户主动提供的身体测量、活动限制、食物过敏与禁忌、口味、用餐环境、预算和目标。只在建议确实依赖某项信息时补问，记录功能始终可先使用。

饮食约定包括用户明确的规则、规则来源、适用范围及生效时间。来源可为用户自己的决定或其提供的专业建议。一般偏好、必须避开的限制、待采纳建议分别处理，不用一段自由文本代替全部约束。

不把本人的当前体重、步数、热量或阶段目标写成通用默认值。活动受限时，推荐遵守当前限制；恢复或要求改变后可以更新。具体饮食安排考虑个体健康与营养需要，依据见[卫健委体重管理指导原则](https://www.nhc.gov.cn/ylyjs/zcwj/202412/75cb79c171c94def9e768193e65484f7/files/1736390749000_59785.pdf)及 [WHO 健康饮食原则](https://www.who.int/news-room/fact-sheets/detail/healthy-diet)。

### 记录实际发生的饮食与体重

饮食记录保存发生时间、餐次、食物、用户描述的份量、实际吃下或剩余情况、来源，以及必要的估算。允许一句话、图片和快速操作，也允许补记、跳过与自然纠正。

推荐方案、计划吃什么和实际吃了什么分开保存。未记录、明确没吃和已经记录是不同状态。照片不能证明精确克数；估算热量或营养时展示范围、依据及缺失份量，不能伪装成精确摄入。

体重支持单位和测量日期，保留原始记录。趋势基于同口径的有效测量，显示样本覆盖；记录太少时展示记录，不制造趋势。单日波动不触发惩罚或自动降低摄入目标。步数作为可选活动记录，首版支持手动与截图输入。

### 下一餐建议与饮食控制

健康 Agent 根据有效饮食约定、最近记录、可用餐食与用餐条件生成少量选项。每个选项包含食物组合、份量描述、可替换项、与约定的关系，以及有依据时的费用或营养估计。

用户提供菜单时围绕菜单做选择；没有真实商家、价格或供应依据时给食物类型与做法，不编造附近餐馆、实时价格或库存。

用户说“就选第一个”“今天没条件做，换一个”时，建议与采纳、替换或放弃的反馈关联保存。下一次回顾可以跟进这次选择和困难，再调整后续建议。未回复只表示未知，不要求用户维护一套执行状态；实际饮食记录到来后再核对能够确定的结果。

过敏、明确禁忌和活动限制作为候选校验条件。识别到冲突时移除候选或解释需要补充的信息，不能为满足预算牺牲硬性限制。财务服务只提供餐费相关摘要，健康服务无需读取全部账户与流水。

建议应帮助调整下一餐和日常习惯，不自动开启极端摄入限制、禁食、药物或惩罚性运动。用户反馈饥饿、难执行或身体不适时优先重新评估建议，必要时建议获取专业帮助。

## 监督与回顾

监督由已约定的提醒、基于真实记录的反馈和可修改的饮食约定组成。默认不产生连续催促；提醒时段、频率上限、安静时间、语气和暂停范围由用户选择，服务保留简单建议值供修改。

| 时机 | AI 与程序的职责 |
| --- | --- |
| 用户问下一餐 | AI 读取当前约定与记录，生成可执行选项；程序校验关键限制 |
| 新增或纠正饮食 | 程序更新记录与统计；AI 按需解释与约定的关系，不为每笔生成长报告 |
| 约定用餐时段 | 当前设备展示已排期提醒；打开后读取最新建议与记录 |
| 用户请求回顾或到约定回顾时间后打开 App | AI 对照已记录情况、体重趋势及困难，总结一项下一步调整 |
| 改规范、暂停或说今天别催 | 程序更新有效范围，并取消或重排相关提醒 |

首版采用本机用餐时段提醒，滚动排期未来 14 天，配合服务端 AI 建议与回顾。已同步的提醒可以在普通退出 App 后由系统呈现；具体送达受通知权限、电池策略和系统运行状态影响，必须实体手机验收。不承诺精确到分钟。

本机提醒不能根据设备尚未同步的餐食或服务器变化实时抑制。App 关闭后的动态个性化推送需要另外接通服务端到手机的投递链路，列为后续增强；不得将本机提醒宣传为该能力。

提醒文案使用中性邀请，不因没记录而断言没吃，也不因未回复而升级催促。短暂断网时保留已同步摘要和草稿，输入明确显示尚未提交，恢复后继续原请求。网络正常但模型不可用时，仍可通过直接操作记账、记饮食、记体重。“今天不提醒这台手机”在本机持久保存并可离线取消当天排期，不把离线暂停说成服务端偏好已修改。过期提醒不在恢复后集中补发，长时间不打开 App 超出排期范围后不承诺继续提醒。

## Agent 与数据的一致性

主知行保持统一人格，负责理解需求、委派与解释整体情况。财务子 Agent 使用财务记录、预算与查询工具；健康子 Agent 使用饮食约定、饮食与体重记录、推荐和回顾工具。用户在服务页细聊与在主知行聊天，得到同一份有效数据。

金额、日期、预算和统计由程序计算。AI 负责提取、归类、建议与解释；只有真实工具回执才能支撑“已记录”“已修改”“提醒已安排”。

目标与偏好可通过共享记忆帮助理解，但财务与健康数据以对应服务记录为准。后台来源、生效时间、修改记录和幂等标识支持纠错与恢复，不要求用户管理这些内部状态。

保留普通聊天需要的运行、队列、取消、重试和子 Agent 委派。移除工作与任务的产品入口时，旧数据保留，旧通用主动计划停止继续触发，并给出简短升级说明。

## 首版完成条件

1. 主知行和服务页都能记录、查询与纠正同一笔消费、同一顿饮食和同一次体重；重发与重启不重复写入。
2. 调整某月预算、饮食约定或身体限制后，后续建议与页面立即生效，历史实际记录保留。
3. 一次性消费、房租实际支付、退款与转账不会造成错误总额；数据不足时不宣称结余目标达成。
4. 完整验收“聊出饮食规范、推荐、用户采纳或替换、记录实际饮食、次日回顾引用这次选择与困难、后续推荐相应改变”；重启后关联仍在，建议说明真实依据。
5. 未记录不会被解释为没吃；照片估计、推荐与实际摄入清楚区分，纠正会刷新后续回顾。
6. 在实体 Android 手机上，普通退出 App 后收到约定时段提醒，点击进入正确页面；暂停、修改时段和完成记录后的本机取消有效。
7. 模型不可用但网络正常时可直接记录；断网时保留已同步摘要和草稿，明确未提交，恢复后原请求只提交一次。
8. 移除工作与任务入口后，主聊天、多子 Agent、附件和已有历史仍可使用。
9. 通过仓库要求的验证，完成对应后端部署、数据库备份与迁移验证、固定签名的独立 APK 和实际下载安装回归。
10. Release 附安装包、校验值和升级说明；交付完成意味着本人手机可日常使用。

## 使用后观察

首轮关注实际能否坚持使用：记录与纠正是否顺手、建议是否能照着吃、提醒是否有帮助或打扰，以及预算和体重趋势能否解释。使用本地验收与用户反馈，不为此新增未经请求的遥测。

后续优先解决实际卡点，再决定接入动态推送、更多账单导入、健康平台同步或食物数据源。发布前不继续扩展通用工作功能。
