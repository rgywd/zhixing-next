# 聊天照片

输入框「+ → 照片」直接打开系统相册，可一次选择多张；选完回到输入框，继续写文字或直接发送。照片立即进入本机持久草稿，选择时不依赖网络，也没有另一个「上传」步骤。主知行、财务、健康和首次对话共用此流程。

草稿用紧凑的 96dp 图片缩略图横向排列，不展示截图文件名、大小或文件卡片。右上角叉号移除单张，保留 44dp 点击区域且不覆盖图片中央；点图片打开全屏预览，可左右滑动。发送后的照片也直接显示为图片，分享入口在大图预览中。普通文件仍走独立的资料与产物页。

每条消息最多 8 份附件，已有文件与照片共同占用额度；单份传输最多 20 MiB。系统相册按剩余额度限制选择，取消不会更改草稿。图片保存为应用私有副本，系统清理相册选择器缓存或 App 重启后仍能继续发送；移除和成功发送只清理应用副本，不改相册原件。

点击一次发送，客户端依次准备和传输照片，再提交同一条包含文字及所有照片的消息。中途失败保留整条草稿，不发送缺图的消息；重试跳过已收到回执的照片，并复用未完成照片的上传 ID 与已准备字节。消息提交后未收到确认时，沿用不可变消息 ID 重试，避免重复发送。离开页面中止当前传输，迟到回执不能进入另一个会话。

照片按实际缓存文件格式命名。PNG/JPEG/WebP/GIF 在限制内直接传输；其他格式转成 JPEG，超过服务器 2400 万像素或 20 MiB 的照片先按长边 4096 像素适配，仍超限则提示失败。模型理解图片取决于所选模型的图片输入能力。

交互参考了 RikkaHub 的 [选择图片后直接加入输入状态](https://github.com/rikkahub/rikkahub/blob/a7d1e6efb50bb781e49bc26c5145640ad6a7ea97/app/src/main/java/me/rerere/rikkahub/ui/components/ai/ChatAttachmentPicker.kt) 和 [返回聊天并统一发送](https://github.com/rikkahub/rikkahub/blob/a7d1e6efb50bb781e49bc26c5145640ad6a7ea97/app/src/main/java/me/rerere/rikkahub/ui/pages/chat/ChatPage.kt)；本次查看其源码，未声称运行该 App。缩略图按用户参考改成纯图片展示。

原生接口依据 Expo SDK 57 [ImagePicker](https://docs.expo.dev/versions/v57.0.0/sdk/imagepicker/)、[FileSystem](https://docs.expo.dev/versions/v57.0.0/sdk/filesystem/) 和 [ImageManipulator](https://docs.expo.dev/versions/v57.0.0/sdk/imagemanipulator/)。特别是 `File.copy()` 为异步操作，必须等复制完成后保存草稿。照片能力已在 0.2.8 引入原生依赖，本次修正不增加权限、依赖或后端迁移。

## 验证边界

自动化覆盖原生选择参数、额度、取消、重复打开、过期结果、部分不可读图片、本地异步复制、转换前后持久化、相同字节与 ID 重试、单次发送提交所有图片、部分失败不提交消息、未知消息回执重试、离开中止、欢迎页持久交接和草稿重启恢复。保留文件上传、相册格式适配和原聊天回归。

2026-10-27 使用 Android API 36 ARM64 独立模拟器、合成收据与真实本地 API 实测：首次对话多选两张直接回到输入框，键盘下预览与右上角移除，全屏打开第二张，强制停止后恢复双图与文字，单次发送对应一条含两个资源的消息。已有会话另通过本地代理让第二张返回 503：整条草稿保留，重试仅补传第二张，最终仍是一条双图消息；资源文件 SHA-256 与回执一致。320dp、115% 字号与深色模式另检查缩略图、横向滚动和键盘布局；调整模拟器密度后重启调试宿主再验证相册。测试使用无模型 worker 的隔离服务，没有调用生产视觉模型。调试宿主临时启用开发支持，通过 Metro 加载当前业务源码；该宿主配置不进入提交。

JS bundle、本地自动化、调试宿主原生行为和正式签名 APK 是不同证据。iOS 原生、实体 Android 手机及真实 iPhone HEIC 选择仍未覆盖；正式版本的构建与签名以对应发布回执为准。
